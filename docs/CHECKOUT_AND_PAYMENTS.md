# Checkout и заявки АН-30

## Что уже работает

Checkout creates a заявка (manager request), not a payment -- the owner's
direction has been explicit and repeated: "Пока без оплаты! просто создания
заявок для менеджеров!". There is no payment gateway and no reservation held
by a silently-expiring timer.

AN30-008 реализовал один серверный checkout для клиента с активной сессией и
для гостя; AN30-014 убрал sandbox-платёж и резерв-по-таймеру и заменил их
заявкой. Браузер передаёт только UUID товара и количество. API заново читает
активную цену, проверяет доступный остаток и в одной транзакции:

1. подтверждает, что остатка достаточно для каждой позиции (без удержания —
   ничего не резервируется и не декрементируется);
2. фиксирует снимки SKU, названия и цены;
3. создаёт заказ со статусом `awaiting_confirmation` — заявку, которую видит
   персонал в очереди `/admin/orders`.

Цена, итог заказа и статус никогда не принимаются из браузера. Деньги
передаются и хранятся целыми копейками. Валюта текущего контракта — только RUB.
Менеджер подтверждает заявку по телефону и переводит её дальше по статусам;
оплата и её способ согласовываются отдельно и не проводятся через сайт.

## HTTP-контракт

- `POST /api/v1/checkout` — checkout авторизованного клиента; требует cookie,
  точный `Origin` и CSRF.
- `POST /api/v1/checkout/guest` — гостевой checkout; требует точный `Origin`.
- `GET /api/v1/orders` и `GET /api/v1/orders/:id` — собственные заказы клиента
  или рабочая очередь персонала.
- `GET /api/v1/orders/guest/:id` — гостевой заказ; секрет передаётся только в
  `X-Guest-Order-Token`, не в URL. В БД хранится только HMAC токена, теперь
  прямо в `app.orders.guest_token_hash` (раньше — на резерве).
- `PATCH /api/v1/orders/:id/status` — оптимистичное изменение состояния
  персоналом с обязательным `version`.

Повтор checkout с тем же ключом идемпотентности возвращает существующую
заявку. Повтор ключа с другим payload даёт `409` и не меняет данные.

## Остатки и конкуренция

Checkout берёт shared advisory lock каталога, поэтому импорт 1С не может
одновременно заменить цену или остаток между проверкой и снимком заказа.
Строки `inventory_balances` блокируются в стабильном порядке при чтении, но
остаток не декрементируется и не резервируется — заявка ничего не держит.
Это осознанный компромисс: без оплаты и без резерва по таймеру держать
остаток нечем и незачем, а конфликт за последнюю единицу решает менеджер на
звонке, а не сервер. Две одновременные заявки на последнюю единицу обе
получают `201`.

## Статусы заказа

`awaiting_confirmation` (заявка создана, ждёт звонка менеджера) →
`processing` / `awaiting_delivery_terms` → `ready` → `completed`, либо
`cancelled` на любом этапе до `completed`. Менеджер меняет статус через
`PATCH /orders/:id/status`; переход проверяется сервером и защищён `version`.

## Production gate

Конфигурация использует:

```text
DEPLOYMENT_ENVIRONMENT=development|staging|production
ENABLE_PUBLIC_CHECKOUT=true|false
LEGAL_DOCUMENTS_APPROVED=true|false
```

`ENABLE_PUBLIC_CHECKOUT` — единственный переключатель публичного checkout: он
гейтит и страницу оформления (`apps/web`), и сами API-маршруты `POST
/checkout` / `/checkout/guest` (503, если выключен). По умолчанию выключен и
в production, и локально без явного override; `compose.dev.yaml` включает его
для разработки. Публичный checkout также требует `LEGAL_DOCUMENTS_APPROVED=true`
— иначе API отказывается стартовать с этим флагом включённым.

## Локальная проверка

После запуска Compose очистите только локальные rate-limit ключи, если smoke
повторяется много раз, и выполните:

```bash
docker compose -f compose.yaml -f compose.dev.yaml exec -T api \
  node dist/cli/checkout-smoke.js
```

Smoke проверяет checkout из аккаунта и гостя, защиту гостевого заказа,
конфликт идемпотентного ключа, отклонение клиентской цены строгой схемой,
подтверждение заявки менеджером, суммирование остатка по нескольким складам,
отказ при нехватке остатка и одновременную отправку двух заявок на последнюю
единицу (обе успешны — заявки не держат остаток).
