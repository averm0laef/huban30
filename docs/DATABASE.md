# База данных АН-30

## Назначение и границы

Автономная база начинается с чистой схемы `app`. Данные production-проекта
Supabase не копируются. Production-каталог, цены и остатки будут поступать из
1С; демонстрационный каталог разрешён только в локальном development.

Начальная модель содержит 48 таблиц и 2 представления. Она разделена на области:

- пользователи, клиентские адреса, сотрудники, приглашения, opaque-сессии,
  подтверждение email, восстановление пароля, TOTP и recovery-коды;
- бренды, категории, товары, изображения, избранное, версии цен, склады,
  остатки, движения и атомарные резервы;
- staging-импорт 1С, строки импорта, конфликты, ревизии и неизменяемый журнал
  before/after для отката;
- заказы, неизменяемые снимки позиций и история состояний;
- платежи, webhook-события, возвраты и idempotency keys;
- чаты, участники, доставка/прочтение сообщений и проверяемые вложения;
- контент, баннеры, настройки, защищённые интеграции, персонал, накладные,
  отчёты, outbox и append-only аудит.

## Инварианты

- Все денежные поля `*_kopeks` имеют тип `bigint`; браузер не является
  источником цены или итоговой суммы.
- `order_items` хранит снимок SKU, названия и цены на момент заказа.
- `quantity_reserved` не может быть больше `quantity_on_hand`.
- Ключи внешних webhook и запросов имеют уникальные ограничения для защиты от
  повторной обработки.
- История остатков, история заказов, табель и аудит запрещают `UPDATE` и
  `DELETE` триггерами.
- Окружение БД (`development`, `staging`, `production`) инициализируется один
  раз и затем не может быть изменено обычной миграцией или приложением.
- Товары с `is_demo = true` блокируются триггером вне development.

## Миграции

Миграции находятся в `packages/database/migrations` и имеют формат
`NNNN_name.sql`. Runner:

1. берёт PostgreSQL advisory lock;
2. проверяет, что применённые файлы присутствуют в образе и их SHA-256 не
   изменился;
3. применяет каждый новый файл в отдельной транзакции с `lock_timeout` и
   `statement_timeout`;
4. фиксирует checksum в `public.schema_migrations`;
5. сверяет неизменяемую метку окружения.

Применённые файлы запрещено редактировать. Исправление выпускается следующей
forward-only миграцией. Откат production выполняется восстановлением проверенной
резервной копии либо новой компенсирующей миграцией, в зависимости от инцидента.

Локальный запуск через Node.js требует `DATABASE_URL` или `DB_*` вместе с
паролем/secret-файлом:

```bash
DATABASE_ENVIRONMENT=development pnpm db:migrate
DATABASE_ENVIRONMENT=development pnpm db:status
```

В Compose миграция является одноразовым сервисом и обязана завершиться с кодом
0 до запуска API:

```bash
docker compose -f compose.yaml -f compose.dev.yaml up -d --build
docker compose -f compose.yaml -f compose.dev.yaml logs migrate
```

Статус `Exited (0)` у сервиса `migrate` после старта является нормальным.

## Development seed

Seed идемпотентно создаёт только два явно помеченных демонстрационных товара.
Для запуска одновременно требуются три opt-in переменные, development-метка
самой БД и отдельный Compose-профиль:

```bash
docker compose -f compose.yaml -f compose.dev.yaml --profile dev-tools run --rm seed
```

Production Compose не содержит активного seed-сервиса. Даже при ручной передаче
development-переменных production/staging БД отклонит seed по собственной
неизменяемой метке и триггеру каталога.

## Проверка схемы

Smoke-проверка выполняется внутри транзакции и всегда завершает её `ROLLBACK`:

```bash
docker compose -f compose.yaml -f compose.dev.yaml exec -T postgres \
  psql -U an30 -d an30 < packages/database/verification/schema-smoke.sql
```

Она проверяет контракты ролей и состояний, тип денег, запрет oversell,
append-only аудит, неизменяемость окружения и запрет demo-данных вне development.
