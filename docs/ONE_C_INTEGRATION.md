# Интеграция каталога с 1С

## Что указать в 1С: чек-лист владельца

Делается отдельно для каждой информационной базы (основной и дополнительной).

1. На сайте: «Рабочее место» → «Настройки интеграций» → кнопка нужной базы.
   Задайте имя пользователя, пароль не короче 16 символов и в «Разрешённых
   сетях» внешний IP компьютера/сервера с 1С в виде `203.0.113.10/32`.
   Включите переключатель и сохраните. Пароль после сохранения не
   показывается — запишите его для 1С.
2. В 1С: Администрирование → Настройка синхронизации данных → Обмен с сайтом
   → создайте узел обмена этой базы:
   - адрес сайта — ровно тот, что показан в настройках:
     основная база `https://<домен>/api/v1/integrations/1c/exchange`,
     дополнительная `https://<домен>/api/v1/integrations/1c/exchange/secondary`;
   - пользователь и пароль — из шага 1 (у двух баз они разные);
   - выгружать: товары (с картинками, если нужны фото), цены, остатки;
   - тип цен: тот, по которому магазин продаёт (в базе владельца это
     «Оптовая цена»; «Учетная цена» — себестоимость, её сайт не берёт). Если
     видов цен продажи несколько и нужен определённый, его точное название
     задаётся переменной `ONE_C_PRICE_TYPE` (основная) или
     `ONE_C_PRICE_TYPE_SECONDARY` (дополнительная) на сервере;
   - выгрузку заказов не включайте (сайт её не принимает и ответит ошибкой);
   - сжатие архивом не включайте; размер части файла 1С узнаёт от сайта.
3. Первый запуск — полная выгрузка. Затем регламентное задание: цены и
   остатки каждые 15–30 минут, полный каталог реже (например, ночью). Два
   задания одной базы не должны идти одновременно.
4. Проверка: «Импорт из 1С» → журнал обменов нужной базы. «Готово» — данные
   на сайте обновлены; «Ошибка» — причина написана в строке; пустой журнал —
   1С не достучалась (проверьте включение, адрес, логин/пароль и IP).

Где бренд, марка и фото берутся из выгрузки:

- **Бренд**: `<Изготовитель>`, иначе свойство «Производитель», «Бренд»,
  «Торговая марка» или «Изготовитель», иначе реквизит «Производитель».
  Свойство «Марка» брендом не считается — это марка автомобиля.
- **Марка/применяемость**: свойства «Марка», «Марка автомобиля», «Модель»,
  «Применяемость», «Применимость», «Совместимость» и т. п. Сохраняются в
  закрытых атрибутах товара под своими названиями из 1С и участвуют в поиске
  (запрос «колодки toyota» найдёт товар), но на витрине как проверенная
  совместимость не показываются (см. CATALOG_DATA_STRATEGY.md).
- Все свойства хранятся под названиями из 1С, значения-справочники — текстом.
  Описания свойств (`Классификатор/Свойства`) запоминаются для каждой базы
  (миграция `0033_one_c_exchange_properties_images`), поэтому файл товаров без
  классификатора тоже разбирается правильно.
- **Фото**: `<Картинка>` — файлы, переданные 1С в том же сеансе. JPEG/PNG/WebP
  до 10 МБ, после проверки ClamAV и медиа-пробы; что не прошло — пропускается
  и считается в журнале, обмен не прерывается. Фото, удалённые в 1С, с сайта
  автоматически не убираются.
- **Склады**: остатки хранятся по каждому складу 1С (`<Склад ИдСклада>` или
  `<Остатки><Остаток><Склад>`) с его названием; витрина показывает сумму.
  Если склад не указан, используется общий склад базы.

## Границы и безопасность

1С остаётся единственным production-источником каталога, цен и фактических
остатков. Для двух информационных баз используются независимые подключения,
выключенные по умолчанию. Admin включает каждое только после
сохранения username, нового пароля длиной не менее 16 символов и непустого CIDR
allowlist.

- JSON endpoint с preview/apply: `POST /api/v1/integrations/1c/imports`.
  Этот прежний JSON-транспорт относится к основной базе; служебное
  пространство идентификаторов дополнительной базы здесь отклоняется до staging.
- Стандартный CommerceML endpoint «Обмен с сайтом»:
  `GET|POST /api/v1/integrations/1c/exchange` (`checkauth`, `init`, `file`,
  `import`, только `type=catalog`). Принимаются `import*.xml`, `offers*.xml`
  и отдельные `prices*.xml`/`rests*.xml` выгрузок CommerceML 2.08+.
- Вторая информационная база CommerceML:
  `GET|POST /api/v1/integrations/1c/exchange/secondary` с теми же режимами.
  У неё отдельные логин, пароль, CIDR allowlist, ревизия доступа и сессия.
- Авторизация: HTTP Basic поверх обязательного HTTPS.
- Доступ: только адреса из `allowedNetworks`; Caddy является единственной
  публичной точкой входа, API-порт наружу не публикуется.
- Ограничения JSON: 60 запросов/минуту на HMAC-маскированный IP, 16 MiB на
  request (общий лимит тела запроса API) и максимум 5 000 строк в batch. CommerceML принимает чанки до 8 MiB.
  Временное хранилище каждой базы ограничено 4 GiB и 100 000 файлами, до 512 MiB
  на файл. API обрабатывает один запрос `mode=import` за раз и применяет
  максимум 500 строк за запрос. При параллельном запросе 1С получает `progress`
  и может повторить опрос.
- Пароль хранится только как Argon2id hash и никогда не возвращается API.
  GET сообщает только `hasPassword`.
- Cookie CommerceML привязан к IP и `auth_revision`. Каждый запрос повторно
  проверяет включение интеграции, актуальный CIDR allowlist и поколение
  настроек. Отключение, смена username, пароля или CIDR немедленно прекращают
  действие ранее выданных сессий, включая отключение с последующим включением.
  Абсолютный срок сессии — два часа; запросы его не продлевают. После истечения
  срока нужен новый `checkauth`. При обновлении сначала применяется миграция
  `0028_one_c_session_revocation`; cookie старого формата перестают работать.
- JSON uploads и CommerceML `checkauth` попадают в append-only
  `integration_request_log` без Authorization header и тела запроса;
  пошаговый прогресс `file/import` хранится в `one_c_exchange_runs`.
- Отказ на входе записывается с причиной в `details.reason`: `disabled`
  (обмен выключен), `address_not_allowed` (адрес вне «Разрешённых сетей»),
  `wrong_credentials` (неверный логин или пароль — какой из двух, не
  уточняется), `not_configured` (логин и пароль на сайте не заданы),
  `no_credentials` (запрос без Basic-авторизации). Причину определяет
  `checkExchangeLogin` в `one-c-integration.service.ts`; логин и пароль из
  запроса в журнал не попадают, а 1С получает один и тот же ответ 401.
- Кроме входа записываются: превышение лимита попыток (`exchange_checkauth`,
  429) и отказ на шагах после входа (`exchange_request`, 401 или 429, с
  `details.step` и `details.session`: `absent` — сеанс не предъявлен,
  `not_accepted` — предъявлен, но не принят). Эти записи идут через
  собственный лимит журнала — 10 в минуту с адреса
  (`JOURNAL_RATE_LIMIT` в `one-c-exchange.controller.ts`): журнал только
  дополняется, а запросов после входа разрешено 1 200 в минуту.
- В админке отказы видны в «Настройках интеграций», блок «Отказы на входе»
  (`apps/web/app/admin/views/one-c-rejected-requests.tsx`; тексты «что
  случилось и что сделать» — `one-c-rejections.ts`).

Настройки доступны только admin с `settings:manage`:

- `GET /api/v1/catalog/1c/settings`;
- `PUT /api/v1/catalog/1c/settings`;
- `GET /api/v1/catalog/1c/requests` — журнал с пагинацией и фильтром `succeeded`.

В административных методах `?source=one_c_secondary` выбирает вторую базу;
без параметра сохраняется прежняя основная база. Метод
`GET /api/v1/catalog/1c/sources` возвращает обе настройки без секретов.
`GET /api/v1/catalog/1c/exchange-runs?source=...` (право `catalog:import`) —
журнал прогонов CommerceML: статус, ошибка, счётчики строк и фото. Он
показан в админке в разделах «Импорт из 1С» и «Настройки интеграций».
В админке `/admin/settings` базы переключаются отдельно; можно переименовать
их, скопировать правильный адрес обмена и увидеть время последней загрузки
каталога/категорий отдельно от цен/остатков. Переключение не переносит форму
с одной базы на другую.

## Две базы: изоляция и регулярное обновление

Миграция `0030_multi_source_one_c` сохраняет существующие ID и URL основной
базы и добавляет отдельное владение товарами/прогонами. Для второй базы
внешние ID товаров, групп и склада преобразуются в стабильные ключи с
пространством имён и SHA-256; внутренние ссылки преобразуются тем же способом.
Одинаковые имена файлов, идентификаторы и артикулы двух баз не перезаписывают
друг друга. Синтетические ключи производителей строятся из имени производителя
как прежде и разделяются базами, чтобы не создавать одинаковые брендовые фасеты.
Группы 1С каждой базы хранятся отдельно (`app.one_c_group_mappings`), но
публичных разделов не создают: на сайте одно дерево разделов (см. ниже).

## Разделы сайта и группы 1С

Дерево разделов сайта задано один раз в
`packages/contracts/src/storefront-taxonomy.ts` (12 разделов и их
подразделы, миграции `0024` и `0036`). Группы 1С обеих баз только
сопоставляются с ним. Раздел товара выбирается так:

1. раздел, выбранный сотрудником для группы 1С (или ближайшей
   родительской группы) в «Импорт из 1С» → «Разделы сайта для групп 1С»;
   если выбран раздел верхнего уровня, подраздел уточняется по названиям;
2. название группы, затем названия родительских групп. Исключение: если
   название товара начинается с типа детали другого раздела, побеждает
   название — группы 1С часто смешанные («Масла и смазки», «Автохимия»),
   и «Масло моторное … 5W-40» должно попасть в «Моторные масла», а не в
   «Смазки». Внутри одного раздела берётся более точный подраздел;
3. название товара (аккумулятор без слов «грузовой»/«мото» раскладывается
   по ёмкости: до 25 А·ч — мото, до 110 — легковые, от 130 — грузовые);
4. иначе «Без категории» — эти товары перечислены там же, в «Товары без
   раздела».

После смены правил уже загруженные товары перекладываются кнопкой
«Разложить товары заново» в админке или командой
`node apps/api/dist/cli/catalog-recategorize.js --dry-run` (без `--dry-run` —
применить).

Подраздел выбирается, когда по словам названия подходит ровно один
подраздел; если подходят несколько, побеждает тот, чьё слово стоит в
названии первым («Колодки тормозные дисковые» — колодки), при равенстве
товар остаётся в разделе. Группа товара сохраняется в
`products.one_c_group_external_id` для справки.

Новые обмены раскладывают товары сами. После изменения правил или
сопоставлений — кнопка «Разложить товары заново» (то же делает
`node dist/cli/catalog-recategorize.js`, с `--dry-run` — только отчёт).
Всё выполняется одной транзакцией; разделы, созданные раньше из групп 1С
и оставшиеся пустыми, отключаются, но не удаляются. Товар, созданный
вручную (без кода 1С), не переносится в другой раздел — только уточняется
до подраздела своего раздела.

При пересечении ассортимента записи остаются раздельными. Совпадение одного
артикула не объединяет карточки, цены или физические остатки; автоматического
суммирования двух учётных представлений одного склада нет. Точные пары
нормализованного бренда и артикула можно использовать как кандидатов для
последующей проверенной связи, но источник владения не теряется. Rossko
остаётся отдельным предложением «под заказ», а не собственным складом 1С.

Полный каталог может скрыть отсутствующие товары только своей базы; защитная
проверка размера полного снимка сохраняется. Полный файл с остатками обнуляет
только остатки товаров выбранной базы: отсутствующего товара — на всех складах,
присутствующего — на складах, которых нет в его предложении. Товар, у которого
в файле есть только цена, и файл вообще без остатков (`prices*.xml`) остатков
не обнуляют. Дельта
меняет только переданные строки. Очистка временных файлов `init` выполняется
в папке соответствующей базы. Cookie основной базы не разрешает обращаться
к дополнительной и наоборот; отключение одной не отзывает доступ другой.

Периодический обмен запускает 1С по своему регламентному заданию. В каждой
базе нужно настроить отдельный узел «Обмен с сайтом» с её адресом и доступом,
выбрать полный каталог/классификатор для первого запуска, а затем расписание
обновления цен и остатков. Начальный ориентир — каждые 15–30 минут для
предложений и отдельное расписание полного каталога; окончательный интервал
зависит от объёма и длительности настоящей выгрузки. Два задания одной базы
не должны запускаться одновременно. Работа платформы соответствует
[стандартному протоколу 1С](https://v8.1c.ru/tekhnologii/obmen-dannymi-i-integratsiya/standarty-i-formaty/protokol-obmena-s-saytom/):
1С инициирует `checkauth → init → file → import`, сайт принимает данные.
Не реализован вымышленный опрос 1С по адресу, которого ещё нет.

Поле «Ожидаемый интервал» в настройках служит контролю актуальности:
`current` — последняя загрузка предложений пришла в пределах двух интервалов,
`stale` — задерживается, `never` — ещё не было загрузки, `disabled` —
подключение выключено. Оно не включает регламентное задание вместо 1С.
По умолчанию интервал — 1 440 минут: владелец запускает обмен раз в сутки
(миграция `0052_daily_one_c_exchange`; прежние 60 минут никто не выбирал, и при
суточном расписании исправная база 22 часа в сутки числилась опоздавшей).

Опоздание не остаётся только на странице настроек. Worker раз в час
(`apps/worker/src/one-c-exchange-watch.ts`) ищет включённые базы, у которых цены
и остатки старше двух интервалов, и ставит в outbox событие
`one_c.exchange.late.notify`; сотрудники получают его в Telegram и VK теми же
каналами, что и оповещения чата: «Обмен с 1С задерживается: «Основная база 1С»
не присылала цены и остатки 3 сут. …» со ссылкой на «Настройки». Одно
оповещение на опоздание, повтор раз в сутки, пока обмен не придёт; база, которая
ни разу не обменивалась или выключена, оповещений не даёт. Если Telegram и VK
не подключены (`TELEGRAM_ENABLED`, `VK_ENABLED`), остаётся только значок в
«Настройках».
Для выбора вида цен по имени действуют `ONE_C_PRICE_TYPE` для основной базы
и `ONE_C_PRICE_TYPE_SECONDARY` для дополнительной; без этих настроек парсер
сам берёт вид цен продажи и никогда — себестоимость (см. «Тип цены» ниже).

В локальном UTF-8-контуре 18 ноября 2026 года пройдено 25 HTTP/SQL-проверок
двух подключений: отдельная авторизация, запрет чужого cookie, одинаковые
XML/SKU, независимые файлы/иерархия/цены/остатки, полные и частичные снимки,
две истории актуальности и независимый отзыв доступа. Использовались явно
помеченные демоданные; после проверки настройки восстановлены, тестовые
товары и группы скрыты, остатки обнулены. Это проверка реализации с
синтетическим CommerceML. Настоящие выгрузки и регламентные задания обеих
информационных баз ещё требуют подключения и отдельной приёмки.

19 ноября 2026 года на отдельной БД повторён полный протокол для двух баз с
синтетическими файлами: основная — CommerceML 2.08 (бренд из `<Изготовитель>`
и из свойства-справочника, марка/применяемость, два склада, два типа цен,
фото, помеченный на удаление товар, товар без артикула с реквизитом «Код»,
отрицательный остаток), дополнительная — 2.10 с отдельными `prices`/`rests`
и брендом-строкой. Проверены через публичный API и SQL: бренды, разделы,
цены выбранного типа, остатки по складам, фильтр «в наличии», поиск по
марке, фото, частичный обмен без классификатора, повторный полный снимок
(обнуление складов и скрытие товаров только своей базы), отказ чужого
логина/cookie. Настоящие выгрузки владельца по-прежнему нужно принять на
staging.

## Контракт выгрузки

JSON envelope имеет фиксированную версию. Деньги передаются целыми копейками,
остатки — целыми неотрицательными числами. Каждая сущность содержит монотонно
растущую положительную `version` из 1С.

```json
{
  "schemaVersion": 1,
  "externalBatchId": "catalog-2026-08-01T03:00:00+09:00",
  "exportedAt": "2026-08-01T03:00:00+09:00",
  "rows": [
    {
      "entityType": "brand",
      "externalId": "brand-1c-guid",
      "name": "Производитель",
      "slug": "manufacturer",
      "isActive": true,
      "version": 12
    },
    {
      "entityType": "product",
      "externalId": "product-1c-guid",
      "sku": "AN30-0001",
      "name": "Наименование товара",
      "slug": "an30-0001",
      "brandExternalId": "brand-1c-guid",
      "categoryExternalId": null,
      "description": null,
      "attributes": {},
      "searchText": "AN30-0001 Наименование товара",
      "isActive": true,
      "version": 25
    },
    {
      "entityType": "price",
      "productExternalId": "product-1c-guid",
      "amountKopeks": 159900,
      "currency": "RUB",
      "version": 31
    },
    {
      "entityType": "stock",
      "productExternalId": "product-1c-guid",
      "warehouseExternalId": "warehouse-1c-guid",
      "quantityOnHand": 8,
      "version": 42
    }
  ]
}
```

Поддерживаемые `entityType`:

- `brand`: `externalId`, `name`, `slug`, `isActive`, `version`;
- `category`: те же поля, `parentExternalId`, `description`, `sortOrder`;
- `warehouse`: `externalId`, `code`, `name`, `isActive`, `version`;
- `product`: `externalId`, `sku`, `name`, `slug`, ссылки на brand/category,
  `description`, JSON object `attributes`, `searchText`, `isActive`, `version`;
- `price`: товар, `amountKopeks`, только `RUB`, `version`;
- `stock`: товар, склад, `quantityOnHand`, `version`.

Неизвестные поля запрещены. Slug содержит только lowercase ASCII, цифры и
дефисы. Отключение сущности передаётся `isActive: false`; физическое удаление из
выгрузки не означает удаление на сайте.

## Двухфазное применение

Этот раздел относится к JSON endpoint. Upload не изменяет production-каталог.
Он создаёт staging batch, нормализует
каждую строку и формирует preview:

1. `uploaded/validating` — технические промежуточные состояния одной транзакции;
2. `validated` — доступны counts, conflict report и строки `valid`, `invalid`,
   `skipped`;
3. `POST /api/v1/catalog/imports/{batchId}/apply` — только сотрудник с
   `catalog:import`, только если `invalidRows = 0`;
4. `applied` — создана неизменяемая revision с ordered before/after;
5. `POST /api/v1/catalog/imports/{batchId}/rollback` — компенсирует последнюю
   активную revision и переводит batch в `rolled_back`.

Preview: `GET /api/v1/catalog/imports/{batchId}?limit=100&offset=0&status=invalid`.
Список: `GET /api/v1/catalog/imports?status=validated&limit=50&offset=0`.

Apply сериализован PostgreSQL advisory lock. Между preview и apply повторно
проверяется ожидаемая `source_version`; конкурентное изменение даёт 409 вместо
тихого перезаписывания. Новая цена закрывает предыдущий период и создаёт новую
immutable версию. Остаток обновляется под row lock и не может стать меньше
текущего резерва.

Rollback допускается только для последней активной revision. Он прерывается с
409, если товар/цена/остаток изменены после apply либо новый резерв не помещается
в восстанавливаемый остаток. Inventory history не удаляется: создаётся
компенсирующее `import_rollback` событие. Вставленные catalog rows становятся
soft-deleted tombstones с version 0, чтобы история сохранилась, а следующая
корректная выгрузка могла безопасно их оживить.

## Идемпотентность и конфликты

Payload получает canonical SHA-256. Повтор того же `externalBatchId` и payload
возвращает существующий batch с `idempotentReplay: true`. Тот же batch ID с иным
checksum получает 409. Повторный apply/rollback также идемпотентен.

Preview блокирует apply, в частности, при кодах:

- `schema.*` — повреждённая строка, при этом остальные строки сохраняются;
- `duplicate_entity`, `duplicate_unique_value`, `unique_value_owned`;
- `stale_version`, `version_reused_with_different_payload`;
- `missing_brand`, `missing_category`, `missing_parent_category`,
  `missing_product`, `missing_warehouse`;
- `category_cycle`, `invalid_parent_category`;
- `stock_below_reserved`.

Строка с той же version и теми же данными получает `skipped/noop`, а не создаёт
лишнюю историю.

## Стандартный обмен CommerceML

Кодировка файла берётся из самого файла (`commerce-ml-encoding.ts`): метка
порядка байтов, затем `encoding` в XML-объявлении, иначе UTF-8. Принимаются
UTF-8, windows-1251, cp866, KOI8-R и UTF-16. Файл с другой кодировкой
отклоняется с её названием в причине, а не читается наугад: раньше любой файл
читался как UTF-8, и выгрузка в windows-1251 не разбиралась вовсе.

1С проходит `checkauth → init → file → import`. `mode=file` последовательно
дописывает присланные части `import*.xml` или `offers*.xml` во временное
хранилище. `mode=import` разбирает собранный файл, сохраняет resumable run в
`app.one_c_exchange_runs` и применяет его порциями по 500 строк; ответы между
порциями имеют вид `progress\n...`.

- `СодержитТолькоИзменения` читается со стандартных узлов `<Каталог>` и
  `<ПакетПредложений>`; атрибут корня поддерживается только как legacy fallback.
- `ПометкаУдаления=true` деактивирует товар или категорию, физического удаления
  нет.
- Если `Артикул` пуст, SKU берётся из `<Код>` или предопределённого реквизита
  `Код`; товар без любого стабильного кода не импортируется.
- `<Наименование>` товара сохраняется без пометок сотрудников («(Ш)», «+++»,
  «КОРОБКА 8», «АУДИТ 2023») и без кавычек, оставшихся от загрузки прайса из CSV:
  `publicProductName` в `packages/contracts/src/product-name.ts`. Из очищенного
  названия строятся адрес страницы и поисковый текст; в поисковый текст
  дописываются слова, которыми читается название с сокращениями
  (`catalog-search-reading.ts`). В 1С название не меняется. Подробности и
  замеры — [OWN_CATALOG.md](OWN_CATALOG.md), [SEARCH_ENGINE.md](SEARCH_ENGINE.md).
- Цены принимаются только в рублях. Иная явно указанная валюта не
  переименовывается в RUB.
- В полном `offers.xml` остаток отсутствующего предложения обнуляется, но
  наличие предложения с ценой и без необязательного `<Количество>` не считается
  отсутствием товара.
- Повтор полностью идентичного уже завершённого файла определяется по SHA-256 и
  не создаёт вторую историю цен или остатков.
- Прогон, упавший на временной ошибке, при повторе того же файла продолжается
  с места остановки. Нечитаемый XML фиксируется в журнале обменов как ошибка.
- Бренды общие для двух баз; другое написание того же имени («trw»/«TRW»)
  не переименовывает существующий бренд.

### Цены, остатки и полная выгрузка

- **Тип цены.** Выбор один на весь файл (`selectPriceType` в `commerce-ml.parser.ts`). Из `ПакетПредложений/ТипыЦен` берётся тип, чьё название совпадает с `ONE_C_PRICE_TYPE` (для дополнительной базы — `ONE_C_PRICE_TYPE_SECONDARY`). Иначе отбрасываются типы-себестоимость (в названии «учетн», «закуп», «себестоим») и из оставшихся берётся тип с «розн» в названии, а если такого нет — первый по списку. Если в файле только себестоимость, цены не берутся вовсе. Если файл не называет типов, берётся первая цена каждого предложения. Когда тип выбран, а у предложения цены этого типа нет, цена другого типа не подставляется: у товара остаётся прежняя цена (единственная цена без `ИдТипаЦены` считается ценой выбранного типа). Название взятого типа записывается в журнал обмена (`one_c_exchange_runs.price_type_name`, миграция 0047) и показывается в админке. В базе владельца два вида цен: «Оптовая цена» (продажа) и «Учетная цена» (себестоимость); в узле 1С должна быть выбрана «Оптовая цена» (для УНФ — см. [ONE_C_SETUP_UNF.md](ONE_C_SETUP_UNF.md)).
- **Форматы.** Цена принимается как `1250.50`, `1250,50`, `1 250,50` (до 4 знаков, округление до копейки). Остаток — `5`, `5.000`, `2,5` (вниз до целого); отрицательный остаток = 0. Разбивка по складам важнее общего `<Количество>`.
- **Характеристики.** Предложение `товар#характеристика` относится к товару; остатки характеристик складываются по каждому складу.
- **Одинаковый артикул у разных товаров — норма.** В базе владельца 997 артикулов общие для 2–10 товаров (размер ремня `4PK820` у ремней десяти брендов). Товар определяется идентификатором 1С, а не артикулом; уникального индекса по артикулу нет (миграция 0046). Строка, которую отвергает другой уникальный индекс (слаг бренда, код склада), засчитывается как отклонённая, остальная пачка применяется (savepoint на строку).
- **Полная import.xml** (`СодержитТолькоИзменения="false"`) скрывает товары 1С, которых нет в файле, если файл покрывает не меньше половины активных товаров; иначе ничего не скрывается. Что произошло, записано в журнале обмена (`one_c_exchange_runs.products_hidden`, `hiding_skipped`, миграция 0052) и видно в админке: «снято с витрины: N» или «в файле меньше половины товаров сайта: товары, которых в нём нет, остались на витрине».
- **Первый обмен поверх загруженного каталога.** Каталог, загруженный до обмена из списка номенклатуры, знает товары по коду 1С, а 1С в обмене называет их своим идентификатором. Перед применением товаров файл сверяется с сайтом (`one-c-product-adoption.ts`): товар сайта, чей идентификатор равен коду товара в файле (`<Код>` или реквизит «Код»), получает идентификатор 1С и дальше обновляется в той же строке — с тем же адресом страницы, разделом, выбранным сотрудником, фото, просмотрами и избранным. Так делается в любом файле каталога. Если кода в файле нет, в **полной** выгрузке товар узнаётся по артикулу вместе с названием, когда такая пара одна и в файле, и среди товаров сайта, которых файл не называет; в выгрузке «только изменения» по названию ничего не привязывается. Журнал показывает, сколько товаров привязано. Адрес страницы при обмене не меняется, пока не изменилось название.
  Репетиция на копии тестовой базы владельца (42 723 товара, `one-c-first-exchange.rehearsal.test.ts`, 23.11.2026): с кодом в файле привязаны все 42 723, добавлено 0, скрыто 0, адреса, цены, остатки и разделы не изменились. Без кода: привязано 35 726, 207 добавлены заново (одинаковые артикул и название), а 6 790 товаров без артикула из файла не читаются вовсе и сняты с витрины — поэтому в выгрузке 1С должен быть код номенклатуры. Отправляет ли его 1С:УНФ владельца, покажет первый настоящий файл.
- После завершения обмена сбрасывается кэш дерева разделов, чтобы новые товары сразу появлялись в каталоге.

## Локальная проверка

Smoke создаёт одноразового owner, настраивает TOTP и write-only пароль 1С,
проверяет allowlist, повреждённый batch, preview, idempotency, две ревизии и два
rollback. Catalog rows после проверки не активны, пароль интеграции очищается,
а append-only audit/revision/request journal остаётся как доказательство.

```bash
printf '%s' 'Owner 1C smoke password phrase 2026' | \
  docker compose -f compose.yaml -f compose.dev.yaml exec -T api \
  node dist/cli/create-owner.js --email owner-one-c-smoke@example.invalid \
  --display-name 'Owner 1C Smoke' --password-file /dev/stdin

docker compose -f compose.yaml -f compose.dev.yaml exec -T api \
  node dist/cli/one-c-import-smoke.js
```

### Staging CommerceML smoke

После миграций и deploy стандартный HTTPS handshake проверяется отдельным CLI.
Он не использует `AUTH_DEBUG_TOKENS`, отказывается работать вне окружения и БД
с меткой `staging`, требует точное имя `staging.an30.ru` и дополнительное явное
подтверждение. Если staging-интеграция 1С уже включена, smoke также отказывается
её прерывать.

CLI создаёт случайные одноразовые Basic credentials, сначала определяет IP,
который реально видит API, затем сужает временный allowlist до `/32` или `/128`.
Один стабильный staging-fixture импортируется, получает цену и остаток, а затем
тем же CommerceML помечается удалённым. Это не засоряет публичный каталог новыми
товарами при каждом прогоне и не пытается незаконно удалять append-only историю
остатков и обменов. В `finally` CLI гарантированно скрывает fixture при любой
ошибке, отключает credential, отзывает Redis-сессию, удаляет временные файлы и
восстанавливает прежнюю строку `integration_endpoints` (или удаляет временную,
если строки раньше не было). `integration_request_log`, exchange runs и
inventory events остаются как корректный журнал smoke-проверок.

```bash
sudo AN30_SECRETS_DIR=/etc/an30/secrets \
  docker compose --env-file /etc/an30/staging.env exec \
  -e ONE_C_COMMERCE_SMOKE_CONFIRM=staging.an30.ru -T api \
  node dist/cli/one-c-commerce-smoke.js
```
