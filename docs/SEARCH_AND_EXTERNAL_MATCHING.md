# Поиск и внешнее сопоставление запчастей

Проверено 18–19 ноября 2026 года. Основной каталог, рублёвые цены и собственные остатки читаются из применённой выгрузки 1С. Внешний справочник не участвует в загрузке страницы каталога, не меняет цены и не подтверждает совместимость.

## Поиск по каталогу

Уже использовались нормализация артикула (пробелы, дефисы, точки, косые и кириллические омоглифы), ё/е, русская морфология, неправильная раскладка, опечатки названий, поиск по нескольким словам и подтверждённым кроссам. В шапке работают подсказки с артикулом, брендом и ценой, управление с клавиатуры, Enter, сохранение запроса в адресе и переход к специалисту для VIN. Фильтры и точный запрос не требуют внешнего API.

Добавлено:

- Составные запросы `MANN W 914/2`, `W914-2 манн`, `бош 0 242 235 668` распознаются как артикул с явно названным брендом. Поиск требует соответствующий бренд; таблица поисковых вариантов написания ограничена проверенными брендами.
- Цифровой артикул не подменяется похожим названием или соседним числом по нечёткому совпадению. Префикс и фрагмент артикула остаются допустимыми поисковыми совпадениями и показываются с настоящим артикулом. Это не означает взаимозаменяемость.
- Для запроса конкретного артикула отключён повторный поиск «по любому слову», который мог бы найти бренд и потерять сам номер.
- Обозначения свойств вроде `5W-30`, `12V`, `H7` остаются поиском по тексту, а не распознаются как гарантированный номер детали.
- В запросе заявки «под заказ» удалён идентификатор поставщика: источник выбирает сервер. Название источника отсутствует и в пользовательском интерфейсе, и в сетевом payload формы.

### Как устроен поиск (19 ноября 2026)

Запрос разбивается на слова; товар найден, если **каждое** слово совпало с документом «артикул + название + бренд» хотя бы одним из своих вариантов (`apps/api/src/catalog/catalog-search-tokens.ts`). Варианты только добавляют способы совпасть, исходное слово всегда среди них:

- подстрока слова и, от 4 букв, близкое написание (опечатка `фильр`, `маслянный`, `калодки`);
- лёгкая основа русского слова: `колодок → колодк`, `фильтров → фильтр` (стеммер PostgreSQL не снимает беглую гласную);
- неправильная раскладка (`vfckj → масло`, `ищыср → bosch`) и транслит (`filtr`);
- кириллические двойники в коде или латинском слове (`Н7 → h7`, `МАNN → mann`);
- все написания бренда из курируемой таблицы (`бош`, `lukoil ↔ лукойл`, `лемфордер ↔ Lemförder`, `ликви моли`);
- регулярное выражение для измерений: `5w40`, `5W 40`, `5в-40` находят `5W-40`, но не `15W-40`; `4л`, `4 литра` находят `4 л`, но не `14 л` и `0,4 л`; `600 мм` находит `600/450 мм`; короткое число (`60`) совпадает только целым числом.

Если ни один товар не содержит всех слов, выполняется второй проход «хотя бы одно слово» с более мягким порогом опечатки и близостью ко всей фразе (`matchMode: "any"`). Конкретный артикул так не ослабляется. Пустой ответ по-прежнему ведёт к блоку «под заказ» и заявке специалисту.

Порядок: точный нормализованный артикул → подтверждённый кросс → префикс артикула → название начинается с названного типа детали (`диски тормозные` → сначала «Диск тормозной…») → релевантность ступенями по 0,25 → в наличии раньше отсутствующих → точная релевантность → название. Скрытые, удалённые, товары скрытых разделов и снятых брендов не возвращаются.

SQL строится на каждый запрос (`catalog-search-sql.ts`) из условий, которые обслуживают индексы: триграммный GIN по `search_text_folded` и `sku_normalized` (миграция `0034_catalog_search_trgm_indexes`), btree по `sku_normalized`, полнотекстовые индексы `simple`/`russian`. Слово из двух символов (`h7`) ищется как начало слова через полнотекстовый индекс. Табуляции и переносы строки во вставленном артикуле читаются как пробелы, а не как ошибка запроса.

Набор проверок: `catalog-search-regression-cases.ts` (137 реальных запросов: артикулы в любом написании, двойники, раскладка, ё, формы слов, опечатки, бренды, вязкость/объём, скрытые товары, порядок). Запуск на отдельной базе с миграциями:

```bash
CATALOG_SEARCH_DATABASE_URL=postgresql://localhost/an30_search_scratch \
  corepack pnpm --filter @an30/api exec vitest run src/catalog/catalog-search-regression.test.ts
```

Результат на фикстуре из ~330 товаров: до изменений 106/137, после 137/137. На 50 320 товарах (фикстура + 50 000 синтетических, ноутбук): до — p50 1,1 с, p95 2,9 с и обрывы по `statement_timeout`; после — p50 ≈ 17 мс, p95 ≈ 240 мс, максимум ≈ 0,7 с (широкие запросы с тысячами совпадений и второй проход по опечаткам).

Выбор отдельного движка (PostgreSQL / OpenSearch / Meilisearch), необязательный провайдер OpenSearch и выгрузка в него описаны в [SEARCH_ENGINE.md](SEARCH_ENGINE.md).

Статья пользователя [«Поиск для интернет-магазина: 24 обязательных элемента»](https://habr.com/ru/articles/987394/) использована как список проверок интерфейса: видимая строка поиска, подсказки с данными товара, Enter, сохранение запроса, обработка раскладки и ошибок, фильтры и полезный пустой результат. Поиск запчастей требует более строгой точности, чем общий товарный поиск: похожее название не подтверждает нужную деталь. Автоматический подбор по VIN и утверждение «всегда найдёт нужную» здесь не заявляются.

### Требование к локали PostgreSQL

Для русскоязычного поиска нужна Unicode-совместимая локаль базы. На macOS проверена `en_US.UTF-8`; на Linux подходят корректно установленные UTF-8-локали. Не создавайте базу с `LC_CTYPE=C`/`--no-locale`: при ней PostgreSQL не приводит русскую `Ф` к `ф`, а триграммы могут не распознавать кириллические буквы. Эти операции зависят от локали по [документации PostgreSQL](https://www.postgresql.org/docs/16/locale.html) и [документации парсера](https://www.postgresql.org/docs/16/textsearch-parsers.html).

При реальной проверке выявлена именно такая настройка временной локальной базы. Для проверки создана её копия с `en_US.UTF-8`, перенос выполнен штатным `pg_dump`/`pg_restore`; исходная база сохранена. На исправленной базе прошли 11 проверок реальных SQL-запросов: составной бренд/артикул в трёх формах, разные бренды одного номера, исключение скрытого товара, отсутствие нечёткой подмены номера, многословное название, кириллический бренд, раскладка, пагинация с итоговым количеством, фильтры категории/бренда и фасеты. Проверочные товары откатились транзакцией.

## ReefAPI: что подключено

В админке `/admin/catalog` есть раскрываемый блок «Сопоставление деталей». Он использует закрытые методы:

- `GET /api/v1/catalog/enrichment/status` — доступность и лимит;
- `POST /api/v1/catalog/enrichment/match` — `{ article, brand, mode: "part" | "oe" }`.

Оба метода требуют входа сотрудника с MFA и права `catalog:write`. Публичный каталог эти методы не вызывает. Внешнее сопоставление выключено по умолчанию.

Режим `part` вызывает `autodoc/v1/part_search`: принимает номер производителя детали, но может вернуть разные бренды и альтернативы. Режим `oe` вызывает `autodoc/v1/oem_lookup` только по явному выбору сотрудника, когда известен оригинальный номер автопроизводителя. Эти поиски не равнозначны. Применяемость по конкретному автомобилю в ReefAPI требует отдельного выбора точной модификации и категории; текстовый поиск номера не заменяет этот процесс. См. [официальную документацию ReefAPI](https://reefapi.com/docs/autodoc).

На стороне сервера из ответа допускаются только номер детали, бренд и название. Из них находится точная нормализованная пара **артикул + бренд** в текущем каталоге 1С. Результат показывает кандидата и совпавшие собственные товары. Он не записывает новые цены, остатки или автоматически подтверждённые кроссы. Отсутствие совпадения не означает отсутствие детали: внешний каталог ограничен своим рынком и первой страницей выдачи.

Источник, внешние URL, изображения, внутренние ID, закупочные/зарубежные цены, валюта и внешние остатки не попадают в ответ инструмента. Ключ хранится только на сервере и не возвращается в интерфейс. Никакого внешнего запроса при наборе текста покупателем нет.

## Проверка реального доступа

С существующим локальным ключом выполнен один запрос `part_search` для `W914/2`, рынок `de`, максимум 5 результатов. Получен HTTP 200; стоимость ответа — 2 кредита. Среди результатов одновременно были:

- `MANN-FILTER W 914/2` — масляный фильтр;
- `UNIGOM W9142` — патрубок системы охлаждения.

Это подтверждает необходимость бренда: совпадающий нормализованный номер сам по себе приводит к разным деталям. Оставшиеся строки выдачи также не становятся автоматически подтверждёнными заменами. Ключ в отчёте и репозитории не сохранён.

## Настройки и ограничения расходов

```dotenv
REEFAPI_ENABLED=false
REEFAPI_KEY_FILE=/run/secrets/reefapi_key
REEFAPI_MARKET=de
REEFAPI_DAILY_CREDITS=30
```

Для Compose файл ключа — `AN30_SECRETS_DIR/reefapi_key.txt`; `scripts/init-secrets.sh` создаёт пустой файл, который нужно заполнить перед включением. Для отдельного локального процесса можно указать защищённый файл вне репозитория. Доступен также серверный `REEFAPI_KEY`, но файл предпочтительнее.

Один запрос возвращает максимум 20 строк. Общий для развёртывания лимит расходов резервирует 2 кредита за `part` или 3 за `oe` согласно текущей документации; неуспешные запросы тоже расходуют локальную квоту, чтобы сбои не вызывали повторный расход. Приложение не делает автоматических повторов. Изменение тарифов провайдера потребует обновить этот расчёт.

Кеш допускаемых полей — 6 часов; товары 1С сопоставляются заново при каждой проверке. Redis ограничивает одновременно выполняемый внешний запрос одним; ключ и лимит не передаются браузеру. Таймаут — 20 секунд, предел ответа — 2 МиБ, перенаправления запрещены, проверка TLS включена. При недоступности Redis или провайдера инструмент возвращает понятный статус, основной поиск продолжает работать.

Следующий отдельный этап — ручное подтверждение проверенных связей и пакетное обогащение после импорта 1С. Массовый импорт чужих изображений/описаний и выдача применяемости без подтверждённых данных в этот этап не входят. Условия использования данных описаны в [ReefAPI Terms](https://reefapi.com/terms).
