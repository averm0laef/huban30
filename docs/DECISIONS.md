# Архитектурные решения АН-30

## ADR-001: чистый автономный запуск

- Статус: принято.
- Решение: production-данные Supabase не переносятся. Новая база начинается с чистой схемы, production-каталог поступает из 1С, демонстрационные данные разрешены только в development.
- Причина: исключить перенос неизвестных данных, ошибок RLS и неявных связей legacy-схемы.

## ADR-002: целевой стек

- Статус: принято.
- Решение: pnpm-монорепозиторий, Next.js для storefront и admin, NestJS API, отдельный worker, Node.js 24 LTS, PostgreSQL 18, Redis, Caddy и Docker Compose.
- Развёртывание: VPS минимум 4 vCPU, 8 GB RAM и 100 GB NVMe.

## ADR-003: данные каталога и деньги

- Статус: принято.
- Решение: 1С является источником цены, остатков и каталога. Денежные суммы хранятся целыми копейками. Снимок цены фиксируется в позиции заказа.

## ADR-004: внешние интеграции

- Статус: принято.
- Решение: платежи, уведомления, социальный вход, AI и хранилище подключаются через адаптеры. Базовые функции магазина должны работать при их отключении.

## ADR-005: платежи и доставка

- Статус: принято.
- Решение: товары оплачиваются в checkout, условия доставки согласуются отдельно. Staging использует sandbox. Production checkout технически закрыт до выбора эквайринга, ключей и параметров чеков.

## ADR-006: безопасность доступа

- Статус: принято.
- Решение: opaque-сессии в защищённых cookie, Argon2id, CSRF, rate limit, ротация сессий, серверная RBAC и обязательный TOTP для персонала. Первый владелец создаётся одноразовой CLI-командой внутри контейнера.

## ADR-007: интерфейс и совместимость

- Статус: принято.
- Решение: сохранить логотип, сине-жёлтую палитру, контент, URL и светлую/тёмную тему. Для витрины применить `DESIGN_VARIANCE 4`, `MOTION_INTENSITY 3`, `VISUAL_DENSITY 5`. Для админки использовать плотные рабочие паттерны и TanStack Table, а не маркетинговые блоки.

## ADR-008: домен и отключение legacy

- Статус: принято.
- Решение: целевой домен `an30.ru`, `www` перенаправляется на основной домен. Supabase и Lovable не удаляются и не отключаются до отдельной приёмки и явного подтверждения владельца.

## ADR-009: границы контейнеров и секреты

- Статус: принято.
- Решение: API и worker формируются через `pnpm deploy --prod`, web через Next standalone, поэтому legacy-зависимости не попадают в runtime-образы. Production и staging читают секреты из root-only файлов вне репозитория через Compose secrets. `compose.dev.yaml` использует только заведомо публичные локальные пароли и запрещён для сервера.
- Причина: уменьшить поверхность атаки и размер образов, исключить секреты из image layers и сохранить воспроизводимый локальный запуск на macOS.

## ADR-010: OpenAPI без Swagger UI

- Статус: принято.
- Решение: машинный контракт публикуется на `/api/v1/openapi.json`; Swagger UI не включается, пока совместимый с Nest 11 диапазон `@fastify/static` содержит high-уязвимость.
- Причина: contract generation и будущий типизированный клиент не требуют статического UI, а production-критерий запрещает high-уязвимости.

## ADR-011: forward-only миграции и неизменяемое окружение БД

- Статус: принято.
- Решение: SQL-миграции применяются собственным минимальным runner с advisory lock, транзакцией на файл и SHA-256 журналом. Применённые файлы не редактируются; изменения выпускаются следующей миграцией.
- Решение: каждая БД один раз получает метку `development`, `staging` или `production`. Смена метки и demo-каталог вне development блокируются на уровне PostgreSQL.
- Причина: запуск не зависит от hosted migration-сервиса, конкурентные контейнеры не применяют схему дважды, а ошибочная команда seed не загрязняет production.

## ADR-012: серверная auth-модель и разделение ролей PostgreSQL

- Статус: принято.
- Решение: API работает под отдельной ролью `an30_app` без DDL и административных атрибутов. Владелец схемы доступен только одноразовому migration service.
- Решение: opaque-сессии и CSRF-токены хранятся в БД только как purpose-separated HMAC; staff-сессия получает права только после TOTP и ротации. Права задаются общей типизированной матрицей и проверяются сервером.
- Причина: компрометация API не должна автоматически давать права владельца PostgreSQL; браузер не должен быть источником идентичности или разрешений.

## ADR-013: продуктовый дизайн без шаблонной AI-эстетики

- Статус: принято по прямому требованию владельца.
- Решение: AN30-010/011 используют осмысленную иерархию, реальные рабочие состояния и компоненты дизайн-системы, а не генеративные декоративные шаблоны. Blender применяется только если 3D-визуализация материально улучшает представление товара или бренда.
- Причина: интерфейс должен быть нативным для клиентов и персонала, быстрым и узнаваемым; визуальный эффект не должен ухудшать доступность, производительность или ясность операций.

## ADR-014: двухфазный версионированный обмен с 1С

- Статус: принято.
- Решение: 1С загружает versioned JSON batch через Basic Auth + HTTPS + CIDR allowlist. Upload только валидирует и создаёт preview; сотрудник отдельно выполняет apply. Цена и остаток никогда не принимаются из браузера.
- Решение: повтор upload/apply/rollback идемпотентен. Apply сверяет версии повторно и пишет ordered immutable before/after. Откат возможен только для последней активной revision и создаёт компенсирующие inventory events вместо удаления истории.
- Причина: частичная или повторная выгрузка не должна портить каталог, пересоздавать историю цен, уменьшать остаток ниже резерва или молча перетирать более новую версию.

## ADR-015: резерв до платежа и независимые idempotency boundaries

- Статус: принято.
- Решение: checkout блокирует текущую цену и остаток, затем одной транзакцией создаёт TTL-резерв, immutable order snapshot и pending goods payment. Два checkout за последнюю единицу сериализуются row lock; worker освобождает TTL через функцию БД.
- Решение: checkout, goods/delivery payment, provider webhook и refund имеют отдельные ключи идемпотентности и проверяют повторный payload. Для заказа разрешён только один live goods payment. Доставка создаётся отдельным платежом персонала после оплаты товара.
- Решение: sandbox разрешён в development/staging, но сочетание production + public checkout + sandbox является ошибкой запуска. Боевой адаптер не выбирается до предоставления эквайринга и реквизитов чеков.
- Причина: цена и остаток не должны зависеть от браузера, конкурентный checkout не должен давать oversell, а сетевой retry или повтор webhook — второй заказ, повторное списание товара либо двойной возврат.

## ADR-016: durable chat, безопасные вложения и fail-closed адаптеры

- Статус: принято.
- Решение: PostgreSQL хранит сообщения и монотонный cursor, Redis используется только как realtime fan-out. Потеря Redis-события восстанавливается запросом `afterSequence`; `clientMessageId` защищает от дубля при retry.
- Решение: guest credential никогда не попадает в URL и хранится только как HMAC. Вложения лежат вне web-root; разрешены только три растровых формата после проверки размера, declared MIME и magic bytes. Форматы с активным содержимым закрыты до появления quarantine/AV/sanitizer.
- Решение: SMTP, Telegram и VK — opt-in providers worker через transactional outbox. Storage, notifications, social auth и AI имеют серверные интерфейсы и безопасные disabled реализации; базовый продукт не зависит от них. Поиск остаётся детерминированным независимо от AI.
- Причина: realtime-канал не должен быть источником истины, reconnect не должен терять обращения, гостевой чат не должен давать IDOR, а отключение внешнего сервиса — ломать каталог или заказы.

## ADR-017: доверенный lock-файл внутри Docker build

- Статус: принято.
- Решение: обновление зависимостей и общий quality-gate выполняют полную supply-chain проверку pnpm и production audit. Dockerfile используют `--frozen-lockfile --trust-lockfile`, чтобы собирать контейнеры только из уже проверенного и зафиксированного `pnpm-lock.yaml` без повторных запросов metadata для каждой записи.
- Причина: повторная проверка 882 записей на каждом `install` и `deploy` делала автономную сборку зависимой от доступности npm registry, не изменяя разрешённый граф пакетов. Изменить версии без изменения lock-файла и отдельной проверки по-прежнему невозможно.
