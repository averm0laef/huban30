# АН-30 (an30.ru) — пакет передачи для агента (Claude Code)

> Версия: 25.11.2026. Один файл = установка скиллов + правила работы + ТЗ владельца.
> Сайт: интернет-магазин автозапчастей (Чернышевск, ул. Куйбышева, 118А), **mobile-first**: основной трафик с телефона.
> Язык интерфейса и данных: русский.

## 0. Как пользоваться этим файлом

1. Владелец или агент выполняет **раздел 1** (установка скиллов).
2. Агент целиком читает **разделы 2–9** ДО написания кода.
3. Агент начинает с **Фазы 0 (аудит, только чтение)**. Пока владелец не подтвердил аудит, в поиск, БД и импорт ничего не меняется.
4. Положить файл в репозиторий как `docs/AGENT_BRIEF.md` и добавить в `CLAUDE.md` строку: «Перед любой задачей прочитай docs/AGENT_BRIEF.md».
5. Если что-то в ТЗ противоречит коду, агент не «додумывает»: фиксирует расхождение в `docs/AUDIT.md` и задаёт вопрос владельцу (раздел 9).

## 2. Правила работы агента (как не сломать архитектуру)

### 2.1. Золотые правила

1. **Сначала понять, потом менять.** Фаза 0 — аудит. Без неё код не трогаем.
2. **Один источник истины.** У каждого факта (артикул, кросс, применимость, фото, цена, остаток, название) одно каноническое место хранения. Остальное — производные (индекс поиска, кэш, фиды), которые пересобираются из канона.
3. **Один поисковый сервис на всех.** Шапка сайта, поиск внутри раздела, поиск в каталоге по машине, подсказки, фиды, админка используют одну и ту же функцию поиска. Параллельных «своих» реализаций быть не должно: именно они дают расхождения.
4. **Тесты до рефакторинга.** Сначала фиксируем текущее поведение (baseline), потом меняем. Любой баг = сначала падающий тест, потом правка.
5. **Малые обратимые шаги.** Ветка на фазу, мелкие коммиты, миграции БД только вперёд и с откатом, новая логика за feature-флагами, режим «shadow» (считаем новым поиском в фоне и сравниваем со старым) до переключения.
6. **Ничего не удалять.** Данные и товары «мягко» деактивируются (`is_active=false`), сырые ответы API хранятся.
7. **Не выдумывать данные.** Если кросс/применимость/фото не подтверждены источником, показывать это честно (разделы 5.2, 5.5). «Подойдёт» нельзя писать без подтверждения.
8. **Секреты** (ключи Росско, UMAPI, доступ к 1С) только в переменных окружения, в логи не попадают.
9. Каждая фаза заканчивается отчётом: что сделано, какие тесты, скриншоты «до/после» (390×844), риски, что дальше.

### 2.2. Бренд и дизайн-токены

Сохраняем фирменный стиль АН-30: насыщенный синий (кнопки, акценты), тёмно-синий баннер подбора, жёлтая кнопка «Подобрать», светло-серый фон, скруглённые карточки, шрифт Inter-подобный. UI/UX Pro Max и frontend-design используются как источник паттернов, а **не** для смены бренда. Токены (цвета, радиусы, отступы, размеры шрифтов) вынести в один файл и использовать везде.

### 2.3. Определение «готово» для любой задачи

- Тесты зелёные (юнит + интеграционные + Playwright на мобильном вьюпорте).
- Нет регресса на golden-наборе запросов (раздел 7).
- Нет новых предупреждений в консоли браузера и логах.
- Задокументировано в `docs/` (что изменено и как это откатить).

### 2.4. Какой скилл когда включать

## 4. Фаза 0: что агент обязан выяснить сам (только чтение)

Владелец не до конца знает текущую архитектуру, поэтому агент составляет карту и кладёт в `docs/AUDIT.md`:

1. **Стек и структура**: фронтенд, бэкенд, БД, очередь/cron, где хранятся миграции, как деплоится.
2. **Поиск «как есть»**: какой движок (SQL LIKE, полнотекст, Meilisearch, Elasticsearch, свой), какие поля индексируются, как строится индекс, как обрабатываются запросы из: (а) шапки, (б) поиска внутри раздела, (в) поиска в каталоге по машине, (г) подсказок, (д) VIN. Диаграмма потока запроса. **Список всех мест, где поиск реализован отдельно** (источники расхождений).
3. **Модель данных**: таблицы товаров, брендов, артикулов, OEM, кроссов, применимости, фото, категорий, остатков, цен. Где хранятся «подтверждённые» связи и как это отличается от «непроверенных».
4. **Внешние API (Росско, UMAPI)**: какие методы вызываются, что возвращают (кроссы, OEM, применимость, фото, названия, цены/остатки), лимиты, таймауты, ретраи, что кэшируется, что теряется. Составить матрицу «провайдер × тип данных» в `docs/PROVIDERS.md`.
5. **Импорт из 1С**: формат (CommerceML/XML, REST, файл), частота, что идёт отдельно (каталог vs цены/остатки), идемпотентность, обработка дублей, как новые товары попадают в категории.
6. **Фото**: откуда берутся, где хранятся, кто и когда связывает фото с позицией, как работает показ фото аналога.
7. **Каталог по машине**: откуда деревья разделов, как определяется «доступность раздела для машины», как строятся поколения/комплектации, почему поиск в каталоге «тупой».
8. **Публикации на площадки**: какие площадки сейчас подключены, как формируются фиды, где данные расходятся.
9. **Аналитика и согласие на cookie**: что собирается сейчас, есть ли плашка.
10. **Список рисков и «хрупких мест»** с приоритетами.

Результат Фазы 0: `docs/AUDIT.md`, `docs/PROVIDERS.md`, диаграммы в mermaid, план фаз с оценками. **Дальше только после «ок» владельца.**

## 5. ТЗ: поиск, данные, интеграции

Главный приоритет: **поисковик и корректность**. Человек пишет артикул, оригинальный номер, номер аналога, название или «фильтр ниссан кашкай» (с ошибками) и находит то, что есть на нашем сайте. Названия таблиц ниже условные: агент подгоняет под реальную схему из аудита, а не наоборот.

### 5.1. Единый поисковый конвейер (по ступеням)

Одна функция `search(query, context)`; все точки входа вызывают её. Запрос проходит ступени сверху вниз, результаты сливаются без дублей по каноническому `part_id`.

| Ступень | Что делает |
|---|---|
| 0. Предобработка | trim, схлопывание пробелов, исправление неверной раскладки («ghbdtn» ↔ «привет»), нижний регистр для слов, регистр артикулов сохраняется в отдельном поле |
| 1. VIN | 17 символов, без букв I, O, Q → ветка VIN (декодирование через провайдера, кэш). Неверный VIN → понятная подсказка, а не пустая выдача |
| 2. Идентификаторы | Нормализованный артикул/OEM/кросс: точное совпадение по таблице идентификаторов. Разбор «БРЕНД АРТИКУЛ» («STELLOX 81-00110-SX», «Стеллокс 8100110sx») по словарю брендов. **Нечёткий поиск для артикулов запрещён** (только точный по нормализованной форме и префиксный при ≥4 символах) |
| 3. Намерение «авто + тип детали» | Разбор текста на токены: марка авто, модель, поколение/год/двигатель, тип детали, прочее. Выборка по применимости (5.5) |
| 4. Полнотекст | Названия, бренд, характеристики; допускается опечаточная устойчивость на словах (не на артикулах) |
| 5. Внешние API | Только если локально мало/нет результатов и запрос похож на идентификатор или авто+деталь. Таймаут 2–3 с, circuit breaker, всё найденное **сохраняется** (5.3) |
| 6. Ноль результатов | «Заявка на подбор» с автоматически приложенным запросом, авто и VIN; запрос уходит в журнал для разбора |

**Ранжирование (по убыванию):** точный артикул нашей позиции → «бренд+артикул» → OEM-совпадение → подтверждённый аналог → подходит по применимости → нечёткое совпадение по названию. Внутри ступени: в наличии выше «под заказ», затем популярность (просмотры, продажи), затем цена.

**Каждый результат несёт причину попадания** (для UI-бейджей, отладки и тестов):

```json
{
  "part_id": 123,
  "matched_as": "analog_of_query | exact | oem | fitment | fuzzy",
  "matched_via": { "identifier": "STELLOX 81-00110-SX", "relation": "analog", "source": "umapi", "status": "confirmed" }
}
```

**Группировка выдачи:** «Точное совпадение» → «Аналоги (подтверждены)» → «Подходит к вашему авто» → «Под заказ по каталогу».

### 5.2. Кроссы, OEM, аналоги

Требование владельца: **если связь официально подтверждена, то запрос по любому номеру из связи выдаёт нашу позицию с пометкой «Аналог»**. Пример: поиск `STELLOX 81-00110-SX` → карточка нашего фильтра KF6009SP с плашкой «Аналог запрошенного STELLOX 81-00110-SX».

Модель (условно):

- `part` — каноническая позиция (бренд, основной артикул, категория, `external_id_1c`).
- `part_identifier` — все номера позиции: `kind` (own | oem | cross | ean), `raw`, `norm`, `brand`, `source`, `first_seen_at`, `last_verified_at`.
- `part_link` — **попарные** связи «A ↔ B»: `relation` (oem_equivalent | analog | replacement | supersedes), `status` (confirmed | unconfirmed | rejected), `source`, `confidence`, `evidence` (ссылка/ид в ответе провайдера).

Правила:

1. **Нормализация идентификатора** (одна функция на весь проект): верхний регистр, удаление пробелов, дефисов, точек, слэшей, подчёркиваний; визуальные двойники кириллицы → латиница (А→A, В→B, Е→E, К→K, М→M, Н→H, О→O, Р→P, С→C, Т→T, Х→X). Хранить и `raw`, и `norm`. Юнит-тесты на десятки вариантов написания.
2. **Транзитивность не вычисляется автоматически.** A≈B и B≈C не значит A≈C. Разворачиваем максимум на один шаг от запрошенного номера, и только по `confirmed`.
3. **В выдаче как «Аналог» показывается только `confirmed`.** `unconfirmed` — только в блоке «Возможные замены, уточните у менеджера», без слова «подходит». Для тормозов, рулевого и подвески нужна особая осторожность.
4. Матрица «источник → статус по умолчанию» настраиваемая (согласовать с владельцем): официальный каталог/кросс производителя → confirmed; кросс из прайса поставщика → confirmed или unconfirmed (решение владельца); ручной ввод менеджера → confirmed с отметкой автора; парсинг названия → unconfirmed.
5. Направленность: OEM → заменители (many), аналог ↔ аналог (симметрично), `supersedes` — односторонняя замена номера.
6. Поиск по OEM: `87139-28010` → выдаются **наши** позиции с этим OEM в `part_identifier`, плюс подтверждённые аналоги. В характеристиках карточки OEM-номера выводятся списком, каждый номер кликабелен (запускает поиск).
7. Аналоги «по каталогу» (которых нет на складе) открываются как **полноценные карточки товара** (под заказ, «Уточнить наличие»), а не как заглушки. Страницы без остатков и данных по умолчанию `noindex`, пока не появятся фото/характеристики (чтобы не плодить тонкие страницы).

### 5.3. Самообучение и индексация (петля данных)

Цель: каждый запрос клиента делает поиск для следующего клиента лучше.

1. **Журнал поиска** `search_log`: исходный и нормализованный запрос, распознанное намерение, количество результатов, клик, добавление в корзину, сессия, время. Без персональных данных.
2. **Кэш и запись ответов провайдеров:** сырой ответ → `provider_raw` (с версией провайдера и датой), нормализованное → в каноническую модель. Следующий клиент получает результат из БД, без API.
3. **Событийная переиндексация:** при появлении новых идентификаторов, связей, применимости, фото, при импорте из 1С, при правке в админке отправляется событие `PartChanged(part_id)`, единый сборщик документа индекса пересобирает позицию (все идентификаторы + подтверждённые кроссы + текст применимости + категория + остатки + популярность). Индексация идемпотентна, полная пересборка без простоя (новый индекс → переключение алиаса).
4. **Добор по популярности:** фоновая очередь с лимитами провайдеров, приоритет по просмотрам/продажам/частоте в `search_log`. Обогащает: кроссы, OEM, применимость, фото, характеристики.
5. **Еженедельный отчёт:** топ запросов без результата, топ запросов с кликом на 3+ позиции ниже, кандидаты в словарь синонимов, конфликты данных (разные провайдеры дают разные кроссы).
6. **Сценарий владельца:** клиент искал «фильтр ниссан кашкай», фото/применимость подтянулись по API и сохранились → следующий клиент получает это уже из БД.

### 5.4. Фото: цепочка разрешения

Для каждой позиции единая функция `resolvePhoto(part)`, по порядку:

1. Собственное фото магазина.
2. Фото производителя именно этой детали → бейдж «Фото этой детали · БРЕНД АРТИКУЛ».
3. Фото **подтверждённого** аналога → бейдж «Фото аналога · БРЕНД АРТИКУЛ» + текст «Деталь может выглядеть иначе: пришлём фото со склада по запросу». Выбираем лучший вариант по правилам (ровный фон, ракурс, разрешение).
4. Плейсхолдер (компактный) + кнопка «Попросить фото у магазина».

Дополнительно:

- Фоновый добор фото для ходовых позиций по популярности (D-14). Пример: для нашей детали есть аналог ST-46420-28400, у аналога фото есть → цепочка должна подставить его с пометкой.
- Фото кэшируем у себя (сжатие, WebP/AVIF, размеры под сетку/карточку), не хотлинкуем у провайдеров. **Проверить права на использование фото производителей** (у части изображений водяные знаки Stellox, Lynx).
- Листинг, карточка, меню и фиды берут фото только через `resolvePhoto`.

### 5.5. Применимость и блок «Подойдёт к вашему автомобилю?»

Модель: `vehicle` (марка, модель, поколение, годы, двигатель, кузов) и `part_fitment` (`part_id`, `vehicle_id`, `source`, `status`, `verified_at`).

Состояния блока на карточке (как в идее Autodoc «select vehicle to confirm compatibility»):

| Состояние | Что показываем |
|---|---|
| Автомобиль не выбран | «Выберите автомобиль, чтобы проверить совместимость» + кнопка выбора |
| Подтверждено для выбранного авто | Зелёная отметка «Подходит для Nissan AD 1.2 · 2006» + источник |
| Для выбранного авто не подтверждено | «Совместимость не подтверждена. Проверим по VIN», кнопка заявки, подтверждённые аналоги для этого авто |
| Нет данных применимости вообще | **Без** кнопки «Все машины». Текст «Применимость уточняется» + заявка/чат |
| Есть список применимости | Раскрывающийся список «Все машины, к которым подходит», сгруппированный по марке/модели |

Применимость, найденная по API, **сохраняется** и используется в следующих запросах («фильтр ниссан кашкай»).

### 5.6. Названия

- Из API сохранять **как есть** (поля вроде `provider_title_raw`, `provider_generic_name`, язык, источник), **но в интерфейсе пока не использовать** (флаг `USE_PROVIDER_TITLES=false`). В будущем из них строятся красивые названия.
- В UI используется `title_display`, собираемый по правилам: `Тип детали` + `Бренд` + `Артикул` + 1–2 ключевых параметра (размеры, спецификация, объём). Скобки, внутренние коды и склейки через « / » не выводятся в заголовок; полное название остаётся в характеристиках.
- Длинные заголовки: максимум 2 строки в листинге (line-clamp), полный текст на карточке.

### 5.7. Текст, опечатки, словари, каталог по машине

**Словари (в БД/файлах, с версионированием, тестами и админ-правкой):**

- `vehicle_brand_alias`: Nissan = Ниссан = Нисан = Nissan; `vehicle_model_alias`: Qashqai = Кашкай = Кашкаи = Qashqai (поколения J10/J11/J12).
- `part_type_synonym`: колодки = тормозные колодки; «давления/регулятор давления/датчик давления» → набор разделов; фильтр салона = салонный = пыльцевой; «щётки» = дворники = стеклоочиститель.
- `brand_alias` деталей: STELLOX = Stellox = Стеллокс; LYNXauto = Lynx.
- Стоп-слова, единицы и спецификации (DOT-4 = DOT4 = ДОТ 4; 5W-30 = 5w30; G11/G12 для антифриза).

**Опечатки:** допуск по Дамерау-Левенштейну на словах (1 ошибка для слов 4–6 символов, 2 для 7+), триграммы, морфология русского (стемминг), исправление раскладки. Артикулы и OEM к нечёткому поиску не допускаются. При сомнении интерфейс говорит «Вы искали: …» и предлагает вариант, а не молча подменяет.

**Сценарий владельца:** «фильтр Ниссан кашкай» (в том числе «фильтер нисан кошкай») → токены: тип = фильтры, авто = Nissan Qashqai → по `part_fitment` находятся подходящие масляные/воздушные/салонные/топливные фильтры, включая нашу позицию LAC-201C, если применимость включает Qashqai. Если поколение не указано, показываем выбор поколения (без дублей, D-09), выдачу не блокируем.

**Каталог по машине (D-10):** доступность разделов для машины считается из применимости (а не вручную). Поиск внутри каталога по машине использует тот же `search()` с фильтром по авто, ищет по названиям деталей, синонимам и идентификаторам. Запрос «Давления» ищет не раздел с таким названием, а детали/разделы, связанные с давлением. Если раздела нет, предлагаются ближайшие и «Заявка на подбор». После выбора комплектации редирект ведёт в раздел с уже применённым фильтром авто.

### 5.8. Провайдеры API (Росско, UMAPI)

Единый слой адаптеров, остальной код про конкретного провайдера ничего не знает:

```
CrossProvider      -> findCrosses(identifier)
FitmentProvider    -> findFitment(part | vehicle)
PhotoProvider      -> findPhotos(part)
VehicleProvider    -> decodeVin(vin), listGenerations(brand, model)
PriceStockProvider -> getPriceStock(identifiers)   // если Росско отдаёт
```

Что реально отдаёт каждый провайдер, определяет Фаза 0 (`docs/PROVIDERS.md`). Требования: таймауты, ретраи с backoff, лимиты, circuit breaker, идемпотентные запросы, сохранение сырого ответа, мэппинг в каноническую модель, тесты на **записанных фикстурах** (в CI живых вызовов нет), мониторинг ошибок и квот, ключи только в env. Конфликты данных между провайдерами пишутся в отчёт, а не решаются молча.

### 5.9. Импорт из 1С

Владелец подключит базу, импорт проверяем напрямую из 1С.

1. **Контракт:** формат и транспорт зафиксировать в `docs/IMPORT_1C.md` (поля, обязательность, типы, примеры). Внешний ключ — стабильный `external_id_1c` (GUID/код), а не артикул.
2. **Конвейер:** приём → `staging_1c_*` (сырьё) → валидация → нормализация (артикул, бренд, единицы) → diff с текущей БД → применение → события переиндексации и добора данных.
3. **Два потока:** каталог (редко, тяжело) и цены/остатки (часто, быстро, точечное обновление без полной пересборки индекса).
4. **Режимы:** `--dry-run` (только отчёт), применение, откат последней партии. Отчёт: новых / изменённых / деактивированных / ошибок, топ проблем.
5. **Идемпотентность:** повторная загрузка того же файла ничего не меняет. Удаление только мягкое.
6. **Распределение новых товаров по категориям:** правила-словарь (ключевые слова, бренд, единицы измерения, шаблоны артикулов) + скрипт классификации с оценкой уверенности. Низкая уверенность → очередь «Требует разбора» в админке. Решения менеджера дополняют словарь (самообучение правил).
7. **Дубли и грязные данные:** дубли артикулов, артикул в кириллице, пробелы и переводы строк, пустой бренд, нулевая цена, отрицательные остатки — каждая ситуация имеет правило и тест на фикстуре.
8. **Нагрузка:** импорт не блокирует сайт; пакеты, транзакции по партиям.
9. После импорта: переиндексация изменённых позиций, постановка в очередь добора (кроссы, применимость, фото), приоритет по популярности.
10. Логи, метрики длительности, алерт на «импорт не приходил N часов».

### 5.10. Публикации на площадки

Все фиды строятся из одной канонической «витрины» (`published_view`), а не из разных источников:

- Генератор на каждую площадку (формат/требования площадки), валидатор схемы, `--dry-run`.
- **Quality gate:** без цены, артикула, бренда, категории или допустимого фото позиция не публикуется (с причиной в отчёте).
- Различия по площадкам (наценка, название, комиссия) задаются **явными параметрами**, а не скрытой логикой.
- **Сверочный отчёт**: сайт ↔ фиды ↔ 1С по цене, остатку, названию, фото. Расхождения = баг.
- Ссылки с площадок ведут на корректные карточки; название, артикул, бренд на сайте и в фиде совпадают.
- Список площадок владелец укажет (раздел 9).

### 5.11. Персонализация и блоки на главной

Принцип: прозрачные правила и скоринг, без «чёрного ящика». ML не нужен на старте.

**Сигналы:** просмотры карточек (вес 1), клик из поиска (2), добавление в корзину (5), покупка (8), выбранный автомобиль («гараж», вес 10 и постоянный), категории, поисковые запросы. Затухание по времени (период полураспада ~14 дней).

**Блоки (порядок на главной зависит от сигналов):**

1. «Для вашего авто» (если есть гараж; **жёсткий фильтр по применимости**, неподходящее не рекомендуем).
2. «Вы смотрели» / «Продолжить подбор».
3. «С этим берут» (правила комплектности: масло → масляный фильтр, колодки → диски/датчик износа, антифриз → …; затем реальные данные покупок).
4. «Популярное в разделе» и сезонное (холодный старт без данных).
5. «Новое в наличии».

**Скоринг кандидата:** `интерес × подходит_авто × наличие × популярность × свежесть`, диверсификация (не больше 2–3 позиций одной категории подряд), позиции без остатка не в топе, без фото и цены не показываем. Логировать показы и клики для оценки блоков (CTR, add-to-cart).

**Согласие:** персональные блоки на основе поведения работают только после согласия на персонализацию; без него показываем контекстные («Популярное», сезонное).

### 5.12. Плашка cookie (в стиле АН-30)

- Нижний bottom-sheet в фирменных цветах, не перекрывает нижнюю навигацию (учесть safe-area).
- Короткий текст + кнопки «Принять все», «Только необходимые», «Настроить» **равной заметности** (без тёмных паттернов).
- Категории: необходимые (всегда), аналитика, персонализация/маркетинг (по умолчанию выключены).
- До согласия аналитика и маркетинговые скрипты не грузятся. Выбор хранится с версией политики; изменить можно из футера.
- Формулировки и состав согласий согласовать с юристом (требования 152-ФЗ и политики обработки персональных данных).

## 6. UI/UX на телефоне: компактно, понятно, продаёт

Эталон по подаче: карточки в стиле Ozon. Цель: меньше визуального шума, больше пользы на экран. Макет сначала в Claude Design (или frontend-design + ui-ux-pro-max) на ширине 375–390 px, утверждение владельцем, затем код.

### 6.1. Листинг (D-04, D-05, D-06)

- **Плитка**: 2 колонки, квадратное фото сверху (1:1), цена крупно, название до 2 строк, строка «Бренд · артикул» мелким, чип наличия («В наличии 242 шт.» / «Под заказ»), компактная кнопка «В корзину» (после добавления — степпер − 1 +).
- **Список**: строка 88 px миниатюра + название + цена + кнопка справа. Переключатель реально меняет раскладку, выбор запоминается (необходимое cookie/localStorage).
- Бейджи (максимум 1–2 на карточке): «Аналог», «Фото аналога», «Под заказ», «Хит».
- Нет фото: компактный нейтральный плейсхолдер, без больших блоков «Фото по запросу».
- Фильтры и сортировка: кнопки-чипы над списком, открываются в **bottom-sheet** с счётчиком «Показать N»; подписи не обрезаются. Активные фильтры видны чипами с «×».
- Скелетоны вместо прыжков вёрстки; бесконечная прокрутка или «Показать ещё» (вместо загрузки по 24 без индикации).
- Блок «Не нашли нужную деталь? Заявка на подбор» компактный, один раз в конце и при пустой выдаче, не перед товарами.

### 6.2. Карточка товара

- Блок цены/наличия/«В корзину» видны без прокрутки; sticky-панель «цена + В корзину» при прокрутке.
- Блок совместимости по состояниям (5.5).
- Бейдж фото (5.4) и пояснение — компактные.
- «Аналоги и замены» — карточками сразу (D-08), «Показать все» при длинном списке.
- Характеристики: OEM-номера списком, каждый кликабелен.
- Доставка/самовывоз: понятный текст («Самовывоз: ул. Куйбышева, 118А, ежедневно 09:00–19:00»). «Срок и стоимость уточнит менеджер» заменить на конкретику, когда это возможно.
- Хлебные крошки (D-01): единый компонент, разделители выровнены, длинный путь прокручивается горизонтально.

### 6.3. Бургер-меню и навигация (D-07)

- Иконки есть у всех категорий **и подкатегорий** (или аккуратный fallback), единый размер, lazy-load, явные размеры (без прыжков).
- Аккордеон без дёрганья, закрытие по тапу вне меню, фокус-ловушка, поддержка скринридеров.
- Меню по машине: показывает только доступные для авто разделы (идею довести до идеала по 5.7).

### 6.4. Общие требования

- Тач-зоны ≥ 44×44 px, контраст ≥ 4.5:1, `font-size` инпутов ≥ 16 px (чтобы iOS не зумил).
- Безопасные зоны (notch, home indicator), нижняя навигация не перекрывает контент и cookie-плашку.
- Скорость: LCP < 2.5 с на мобильном 4G на листинге и карточке, фото в WebP/AVIF с `srcset`, CLS < 0.1.
- Проверка на ширинах 360, 375, 390, 412, 430 px; iOS Safari и Chrome Android.
- Тексты: прямые, без воды; цена и наличие важнее декоративных элементов. Один основной акцентный цвет для CTA.

## 7. Golden-набор запросов и приёмка

Файл `tests/golden/search.yaml` — единый набор. Каждая строка: запрос → ожидаемая позиция/группа/причина попадания (`matched_as`). Тест запускается на каждый PR и в shadow-режиме сравнивает старый и новый поиск. Ожидаемые результаты, зависящие от данных, агент сверяет с БД и фиксирует.

| Запрос | Что должно произойти |
|---|---|
| `STELLOX 81-00110-SX`, `81-00110-SX`, `8100110SX`, `81 00110 sx`, `стеллокс 81-00110-SX` | Одна и та же наша позиция (KF6009SP), `matched_as=analog_of_query`, плашка «Аналог…», связь подтверждена |
| `KF6009SP`, `kf 6009 sp` | Точное совпадение, плашка не нужна |
| `87139-28010`, `8713928010` | Наши позиции с этим OEM (в т.ч. LYNXauto LAC143) + подтверждённые аналоги |
| `LAC-201C`, `LAC201C`, `lac 201c` | Фильтр салона LYNXAUTO с фото производителя (190×265×20), точное совпадение |
| `ST-46420-28400` | Позиция, для которой это аналог, с пометкой, фото аналога, если собственного нет |
| `фильтр ниссан кашкай`, `фильтер нисан кошкай`, `qashqai фильтр салона` | Фильтры по применимости Nissan Qashqai; при нескольких поколениях выбор без дублей |
| `колодки лада веста`, `колодки Лада В` (неполный ввод) | Колодки для Лады Весты, при неполном вводе подсказки, а не пустой экран |
| `тормозная жидкость DOT-4`, `dot4`, `ДОТ 4` | Раздел тормозных жидкостей DOT 4, варианты написания равны |
| `антифриз красный 5кг`, `антифриз аляска g11` | Антифриз Аляска-40 G11 5 кг (артикул 00-00026453) |
| `регулятор давления Toyota Crown` | Список поколений без дублей (D-09); после выбора — результаты по поколению или «Заявка на подбор» |
| `Давления` в каталоге по машине | Не «раздел не нашёлся», а ближайшие разделы/детали (D-10) |
| `ghbdtn` | Исправление раскладки, подсказка «Вы искали: привет…» |
| VIN `1HGCM82633A004352`, `Z94CB41AAER123456` | Ветка VIN: подбор по авто, понятные названия разделов |
| VIN с буквой O/I/Q или 16 символов | Понятное сообщение о формате, не пустая выдача |
| Нулевой запрос `xxzzqq` | «Заявка на подбор» с приложенным запросом, запись в журнал |

**Приёмка поиска:** recall@10 на golden-наборе = 100% для идентификаторов (артикул/OEM/кросс); для текстовых запросов — целевая планка договаривается после baseline; ни одного пустого результата для запросов из набора; одинаковый результат из шапки, раздела и каталога по машине (тест «параритета»).

**Приёмка UI:** скриншоты 390×844 до/после для листинга (плитка и список), карточки, меню, крошек, cookie-плашки; отчёт `ux-test`/`a11y-test`; проверка жестами (тач-зоны, прокрутка, клавиатура не закрывает поле).
