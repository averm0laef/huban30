# Проверки поиска на настоящем ассортименте

Регрессионный набор поиска (`apps/api/src/catalog/catalog-search-regression.test.ts`, 163 запроса) идёт на двух сотнях товаров-образцов. Он охраняет правила, но не показывает, как поиск отвечает на ассортименте владельца: там у слова «воздушный» тысяча товаров, названия написаны с сокращениями, а половины «разговорных» слов в названиях нет. Эти два скрипта задают поиску работающего API запросы покупателя и считают, сколько из них получили то, что имелось в виду.

Скрипты только читают: обращаются к `GET /api/v1/catalog/products`. Между запросами — секунда (API даёт посетителю 60 поисков в минуту). Запускать из корня проекта.

| Команда | Что проверяет | Замер 22.11.2026 |
| --- | --- | --- |
| `node scripts/search-checks/everyday-queries.mjs [адрес API]` | 75 разговорных запросов («гранаты», «косточки», «воздушник», «вд40», «помпа», «глушак»…): сколько товаров найдено и сколько из первой десятки — то, что имел в виду покупатель | до работ 59 из 75, после — 72 из 75 |
| `node scripts/search-checks/reading-queries.mjs [адрес API]` | 26 запросов правильным словом по товарам, названным в 1С с сокращением или латинской буквой-двойником («Аром-р», «Предохр.», «п/син», «Cальник»): попал ли нужный товар в первую пятёрку | до работ 11 из 26, после — 22 из 26 |

Адрес API по умолчанию — `http://127.0.0.1:4000`. Код выхода: `0` — не хуже замера, `1` — хуже.

Нужен API, за которым лежит ассортимент владельца: `reading-queries.mjs` называет товары настоящими названиями, а ожидания `everyday-queries.mjs` писались по этой базе. Как поднять такой стенд, не трогая рабочий, — `scripts/storefront-checks/README.md` (раздел «Где взять стенд с разделами»; сайт для этих скриптов не нужен, только база и второй API).

## Что стоит за цифрами

- **Разговорные слова** — таблица `WORD_SYNONYMS` в `apps/api/src/catalog/catalog-search-tokens.ts`. Слово добавляется, когда замер показал, что по нему находится не то или ничего; слова, которые уже находят нужное по самим названиям («помпа», «линки», «глушак»), в таблицу не вносятся.
- **Сокращения и буквы-двойники** — при обмене с 1С в поисковый текст товара дописываются слова, которыми его название читается, но которых в нём нет (`apps/api/src/catalog/catalog-search-reading.ts`). Название на витрине не меняется. У товаров, уже лежащих в базе, поисковый текст обновится при следующем полном обмене.

## Известное, что эти скрипты показывают, но правки не исправляли

- «стойки» находит и стойки стабилизатора, и амортизаторы: слово двусмысленное, покупатель уточняет вторым словом.
- «резонатор» — таких товаров в базе нет, а поиск вместо «ничего не найдено» показывает товары с похожим написанием. Так работает терпимость к опечаткам на длинных словах.
- «масло в коробку» — находятся масла для АКПП, для МКПП нет.
- Четыре товара с сокращениями находятся, но ниже пятого места: по тому же слову есть десятки товаров с полным названием.

## Как добавить слово

1. Запрос и ожидание — в `everyday-queries.mjs`; прогнать и убедиться, что он не проходит.
2. Посмотреть в базе, как деталь названа на самом деле (в 1С бывает несколько написаний: «баллонный» и «балонный»).
3. Случай в `catalog-search-regression-cases.ts` (товар-образец в `catalog-search-fixtures.ts`) и тест плана слова в `catalog-search-tokens.test.ts` — оба должны упасть.
4. Запись в `WORD_SYNONYMS`; оба теста проходят; собрать API и прогнать скрипт ещё раз — ни один прежний запрос не должен стать хуже.
