# Проверки витрины, которых не дают снимки экрана

Снимок показывает, как страница выглядит. Он не показывает, что меню закрывается, пока к нему ведут мышь, что с клавиатуры не добраться до половины ссылок и что страница за минуту тратит весь лимит запросов посетителя. 22.11.2026 все три ошибки прошли проверку снимками на 1440, 768 и 375 px и были найдены только этими скриптами — разбор в `.planning/2026-11-22-catalog-quality-and-1c-import/findings.md`.

Скрипты ничего не меняют: открывают сайт в браузере (Playwright, установленный в проекте, канал `chrome`) и читают. Запускать из корня проекта.

| Команда | Что проверяет | Что нужно |
| --- | --- | --- |
| `node scripts/storefront-checks/catalog-menu.mjs [адрес сайта]` | Меню «Каталог» в шапке на 1440 и 1180 px так, как им пользуется человек: мышь ведётся по экрану шагами, а не прыгает. Панель не закрывается по дороге от кнопки; наведение выбирает раздел; мышь доходит до подраздела шагом, не переключив раздел по дороге; остановка на другом разделе выбирает его после паузы; фокус раздел не переключает; с клавиатуры: кнопка «Подразделы: …» → Tab → подразделы; Escape возвращает фокус; последний раздел докручивается; панель в пределах экрана, прокрутки вбок нет, цели не меньше 44 px | Сайт, у которого в каталоге не меньше трёх разделов с подразделами. Разделы для проверки скрипт выбирает сам |
| `REDIS_URL=… node scripts/storefront-checks/api-requests-per-visit.mjs [адрес сайта]` | Сколько запросов к API сайт делает за одного посетителя за минуту, по областям лимита: главная → меню → `/catalog` → вторая страница → раздел → товар. API считает запросы на посетителя (60 или 120 в минуту); страница, которая спрашивает слишком часто, заставляет покупателя выбить собственный лимит | Сайт в боевой сборке (`next start`; сервер разработки ссылки заранее не подгружает), `redis-cli`, адрес Redis стенда (счётчики лимита, только чтение) и тишина на стенде: скрипт ждёт, пока счётчики обнулятся |

| `node scripts/storefront-checks/auth-flow.mjs` | Регистрация → письмо → подтверждение почты → вход → выход → восстановление пароля → вход с новым паролем, в настоящем браузере и без подмен. Затем те же двери «не с той стороны»: мусор в каждом поле, чужой сайт (другой `Origin`), выдуманный токен, перебор пароля, попытка узнать, занят ли адрес. Письма берутся из очереди так же, как их берёт worker, и сохраняются в `/tmp/letter-verify.html` и `letter-reset.html` — посмотреть глазами | Локальный стенд (сайт и API), `secrets/local_stand.env`, собранный worker (`corepack pnpm --filter @an30/worker build`). Перед запуском — `sh scripts/storefront-checks/auth-reset-limits.sh`: проверка сама исчерпывает лимит входов со своего адреса |

Адрес сайта по умолчанию — `http://127.0.0.1:3000` (у `auth-flow.mjs` — адрес стенда из `APP_ORIGIN`: API не принимает POST с другого адреса).

Коды выхода: `0` — всё прошло; `1` — проверка не прошла (строки `FAIL` или `TOO MANY`); `2` — проверять нечего (в каталоге стенда мало разделов, не задан `REDIS_URL`).

## Где взять стенд с разделами

На рабочем стенде разработчика (`an30_ux_2b40952e`) семь демонстрационных товаров в пяти разделах — для меню этого хватает, для оценки «как выглядит каталог владельца» нет. Стенд с ассортиментом владельца собирается за пару минут и не трогает рабочий:

```bash
createdb an30_catalog_stand
DATABASE_URL=postgresql://localhost/an30_catalog_stand DATABASE_ENVIRONMENT=development node packages/database/dist/migrate.js up
# наполнить базу репетицией обмена (нужны файлы local-data/1c, см. scripts/catalog-placement/README.md)
ONE_C_REHEARSAL_DIR="$PWD/local-data/1c" ONE_C_REHEARSAL_DATABASE_URL=postgresql://localhost/an30_catalog_stand \
  corepack pnpm --filter @an30/api exec vitest run src/one-c-exchange/one-c-exchange.rehearsal.test.ts
# второй API на 4010: те же переменные, что у рабочего стенда, но DATABASE_URL — новая база, PORT=4010, API_BIND_HOST=127.0.0.1
node apps/api/dist/main.js
# второй сайт на 3010 (после corepack pnpm --filter @an30/web build)
cd apps/web && INTERNAL_API_URL=http://127.0.0.1:4010 npx next start --hostname 127.0.0.1 --port 3010
```

После проверки: остановить оба процесса и `dropdb an30_catalog_stand`. Второй API пользуется тем же Redis, что и рабочий стенд: счётчики лимита у них общие (живут минуту), данные не пересекаются.

## Когда запускать

- После любой правки шапки, меню «Каталог», выдвижного меню на телефоне — `catalog-menu.mjs`.
- После правок, которые добавляют на страницу ссылки на разделы и товары или меняют чтение каталога в `apps/web/app/(store)/_lib/catalog-api.ts`, — `api-requests-per-visit.mjs`.
- Сквозные тесты `tests/e2e` (`corepack pnpm test:e2e`) идут на сайте без API: меню там — простая ссылка, и они этих проверок не заменяют.

## Как устроена проверка мышью

Playwright по умолчанию переносит мышь в цель мгновенно. Человек ведёт её через всё, что лежит по дороге, поэтому в скрипте мышь идёт шагами (`glide`: 30 шагов по 40 мс). Если проверка падает, сначала снимите пошаговый журнал — положение мыши, что под ней, что на экране, события с отметками времени, — и только потом правьте код: так была найдена ошибка, при которой раздел переключался в момент прихода мыши на строку.
