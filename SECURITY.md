# Политика безопасности АН-30

## Сообщение об уязвимости

Не публикуйте секреты, персональные данные или эксплуатационные детали в issue и чатах. Передавайте отчёт владельцу проекта по согласованному закрытому каналу с описанием влияния, шагов воспроизведения и затронутой версии.

## Работа с секретами

- `.env`, ключи, пароли, резервные копии и runtime-файлы запрещено добавлять в Git.
- Production-секреты хранятся в root-only файлах вне репозитория и подключаются как Compose secrets.
- Секреты не выводятся в логи, UI, ответы API и сообщения об ошибках.
- Любой случайно раскрытый секрет считается скомпрометированным и должен быть отозван, а не только удалён из файла.

## Обязательная ротация перед запуском

Рабочий чек-лист со статусами находится в `docs/SECRET_ROTATION.md`.

- Supabase publishable/anon key и service-role key.
- Пароли ранее созданных администраторов.
- Пароль или токен обмена 1С.
- Telegram bot token, VK client secret, SMTP password и AI/API-ключи, если они использовались.
- Все ключи эквайринга и webhook-секреты.

Старый Supabase-проект не удаляется без отдельного подтверждения. Ротация выполняется владельцем в панелях соответствующих провайдеров.

## Production gates

- Публичный `init-admin` запрещён.
- Персонал использует TOTP и recovery-коды.
- API работает под отдельной PostgreSQL-ролью без DDL, `SUPERUSER`, `CREATEDB`, `CREATEROLE` и `BYPASSRLS`.
- Все небезопасные методы требуют точный same-origin `Origin`; авторизованные запросы дополнительно требуют CSRF-токен.
- Opaque-сессии ротируются после MFA, имеют абсолютный и idle timeout и отзываются после reset пароля.
- Структурированные API-логи маскируют credential-поля, email и IP до сериализации.
- Endpoint 1С выключен по умолчанию и принимает Basic Auth только поверх HTTPS,
  из CIDR allowlist и под Redis rate limit; сохранённый пароль никогда не возвращается API/UI.
- Request body ограничен 10 MiB; повреждённые строки 1С остаются в staging и не
  могут попасть в каталог без отдельного server-authorized apply.
- Production checkout не стартует с sandbox-провайдером.
- Гостевой заказ читается только по высокоэнтропийному токену в заголовке; в БД
  хранится purpose-separated HMAC, а не сам токен.
- Цена, склад, сумма и статус checkout вычисляются сервером. Резерв, заказ и
  платёж создаются транзакционно, а одна live-оплата товара гарантируется
  уникальным partial index.
- Sandbox webhook требует HMAC-подпись; event ID, checkout, платёж доставки и
  возврат имеют независимые idempotency keys с проверкой payload.
- В production используются same-origin CORS, CSP, HSTS, CSRF и rate limiting.
- Production-зависимости не должны содержать critical/high уязвимостей.
- Метка окружения PostgreSQL неизменяема после инициализации; demo-каталог
  блокируется внутри БД в staging и production.
- История остатков, состояний заказов, табель и audit log являются append-only.
- До переключения трафика обязательно проходят smoke, E2E и проверенное восстановление резервной копии.
